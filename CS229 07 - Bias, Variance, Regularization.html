7.1 Bias and Variance

Every learning algorithm faces a fundamental tension: a model that is too simple cannot capture the true structure in the data, while a model that is too complex memorizes the training data and fails to generalize. This tension is called the bias–variance trade-off, and understanding it deeply is one of the most practically valuable skills a machine learning practitioner can develop. Engineers who have mastered bias and variance diagnosis are consistently more efficient: instead of blindly trying every possible improvement, they identify the root cause of poor performance and target their effort precisely.

To build intuition, consider housing price prediction. Figure 7.1 shows the same six training examples fitted by three models of increasing complexity. A degree-1 polynomial (linear function) fails to capture the visible curvature in the data — it systematically predicts too low on one side and too high on the other. A degree-2 polynomial fits the data well and generalizes gracefully. A degree-5 polynomial (with as many free parameters as data points) passes through every training point exactly, but produces wild oscillations between them that any reasonable person would recognize as nonsensical.

Center: degree-2 fit (green) — approximately correct; the gold dashed line shows the true quadratic. Right: degree-5 fit (red) — overfits; passes through all training points but oscillates wildly between them, fitting noise rather than signal.

7.1.1 Underfitting and High Bias

Definition · Bias

The bias of a learning algorithm is the systematic error it makes due to incorrect assumptions in its hypothesis class. Formally, for an estimator $\hat{f}$ trained on a dataset $\mathcal{S}$ drawn from distribution $\mathcal{D}$: $$\text{Bias}(\hat{f}(\boldsymbol{x})) = \mathbb{E}_{\mathcal{S}}[\hat{f}(\boldsymbol{x})] - f^*(\boldsymbol{x})$$ where $f^*$ is the true target function and the expectation is over random training sets. An algorithm with high bias makes strong, incorrect assumptions about the data; it underfits — it cannot represent the true $f^*$ even with infinite training data.

The term "bias" here has a precise statistical meaning, distinct from the social concept of bias (racial bias, gender bias, etc.) that we rightly seek to avoid in AI systems. In the machine learning sense, a high-bias algorithm has a strong preconception — for example, that housing prices are a linear function of house size — and stubbornly adheres to that assumption regardless of what the data says. The hypothesis class does not contain the truth, so no amount of additional data can fully correct the problem.

7.1.2 Overfitting and High Variance

Definition · Variance

The variance of a learning algorithm is the expected squared deviation of $\hat{f}$ from its own mean across different training sets: $$\text{Var}(\hat{f}(\boldsymbol{x})) = \mathbb{E}_{\mathcal{S}}\!\left[\left(\hat{f}(\boldsymbol{x}) - \mathbb{E}_{\mathcal{S}}[\hat{f}(\boldsymbol{x})]\right)^2\right].$$ An algorithm with high variance is highly sensitive to the particular training set it sees; small perturbations in the training data lead to large changes in the learned hypothesis. It overfits — it memorizes training noise rather than learning the underlying signal.

The name "variance" is apt. Imagine two friends independently collecting $m$ housing sales records. A high-variance algorithm (e.g., a degree-5 polynomial fit with no regularization) will produce completely different prediction functions for each friend's dataset, even though the datasets are random draws from the same underlying distribution. The predictions thus have high variance across different realizations of the training data.

7.1.3 The Bias–Variance Decomposition

The bias–variance trade-off is not merely qualitative; it has a precise mathematical form. For squared-error regression, the expected test error at a single input point $\boldsymbol{x}$ decomposes exactly as follows.

Theorem · Bias–Variance Decomposition

Let $y = f^*(\boldsymbol{x}) + \epsilon$ where $\epsilon \overset{\text{i.i.d.}}{\sim} \mathcal{N}(0, \sigma^2)$ is irreducible noise, and let $\hat{f}$ be an estimator trained on a random training set $\mathcal{S}$. Then: $$\mathbb{E}_{\mathcal{S},\epsilon}\!\left[(y - \hat{f}(\boldsymbol{x}))^2\right] = \underbrace{\text{Bias}^2(\hat{f}(\boldsymbol{x}))}_{\text{systematic error}} + \underbrace{\text{Var}(\hat{f}(\boldsymbol{x}))}_{\text{sensitivity to data}} + \underbrace{\sigma^2}_{\text{irreducible noise}}.$$ The three terms are independent; reducing one does not directly change the others.

Proof

Write $\bar{f}(\boldsymbol{x}) = \mathbb{E}_\mathcal{S}[\hat{f}(\boldsymbol{x})]$. Then: $$\mathbb{E}[(y - \hat{f})^2] = \mathbb{E}[(y - \bar{f} + \bar{f} - \hat{f})^2] = \mathbb{E}[(y-\bar{f})^2] + \mathbb{E}[(\bar{f}-\hat{f})^2] + 2\mathbb{E}[(y-\bar{f})(\bar{f}-\hat{f})].$$ The cross term vanishes because $y - \bar{f}$ depends on $\epsilon$ and $f^*$ (not $\mathcal{S}$), while $\bar{f} - \hat{f}$ has mean zero over $\mathcal{S}$. Expanding $\mathbb{E}[(y-\bar{f})^2] = \mathbb{E}[(f^* - \bar{f} + \epsilon)^2] = (f^* - \bar{f})^2 + \sigma^2 = \text{Bias}^2 + \sigma^2$ completes the proof. □

The decomposition reveals a fundamental constraint: no algorithm can simultaneously minimize bias and variance. Increasing model complexity decreases bias (the model can express the truth) but increases variance (more parameters to overfit the noise). The optimal complexity sits at the minimum of the sum $\text{Bias}^2 + \text{Var}$, which trades off these competing effects. The irreducible noise $\sigma^2$ sets a floor that no algorithm can beat.

Figure 7.2. Training error (blue) and dev/test error (red) as functions of model complexity. Training error decreases monotonically — a more complex model always fits the training set better. Dev error forms a U-shape: it decreases initially as the model captures true structure, then rises as overfitting dominates. The gold dashed line marks the optimal complexity. The shaded purple region represents the variance gap between training and dev error.
Intuition · Reading the Error Curves

The gap between training error and dev error is a direct diagnostic. If both errors are high, the algorithm has high bias — it cannot even fit the training data well, let alone generalize. The fix is to increase model complexity: add more features, use a higher-degree polynomial, or reduce regularization. If training error is low but dev error is much higher, the algorithm has high variance — it has memorized training noise. The fix is to reduce model complexity: add regularization, collect more training data, or reduce the feature set. Understanding which problem you have prevents wasted effort on the wrong remedy.

7.2 Regularization

Once we identify that an algorithm is suffering from high variance, the most powerful and broadly applicable remedy is regularization: explicitly penalizing large parameter values in the optimization objective. Regularization sounds almost too simple — just add one extra term to your cost function — yet it is one of the most widely used techniques across all of machine learning, from linear models to deep neural networks. Do not be deceived by its simplicity.

The core idea is to trade a small increase in bias for a potentially large reduction in variance. By preventing the model parameters from growing very large, we prevent the learned function from making wild excursions between training points. The result is a smoother, more generalizable hypothesis, even if it no longer interpolates the training data exactly.

7.2.1 $\ell_2$ Regularization for Linear Regression

Recall the linear regression objective: $J(\boldsymbol{\theta}) = \frac{1}{2}\sum_{i=1}^{m}(y^{(i)} - \boldsymbol{\theta}^\top \boldsymbol{x}^{(i)})^2$. To add $\ell_2$ regularization (also called ridge regression), we append a penalty on the squared Euclidean norm of the parameter vector:

Regularized Objective
$$J_\lambda(\boldsymbol{\theta}) = \frac{1}{2}\sum_{i=1}^{m}\bigl(y^{(i)} - \boldsymbol{\theta}^\top\boldsymbol{x}^{(i)}\bigr)^2 + \frac{\lambda}{2}\|\boldsymbol{\theta}\|_2^2$$

The scalar $\lambda \geq 0$ is the regularization parameter. When $\lambda = 0$ we recover ordinary least squares; as $\lambda \to \infty$ the second term dominates and forces $\hat{\boldsymbol{\theta}} \to \boldsymbol{0}$, yielding the trivial predictor $h(\boldsymbol{x}) = 0$. At an intermediate value of $\lambda$, the optimizer balances fitting the data against keeping parameters small.

Theorem · Ridge Regression Closed-Form Solution

The minimizer of $J_\lambda(\boldsymbol{\theta})$ over $\boldsymbol{\theta} \in \mathbb{R}^{n+1}$ is: $$\hat{\boldsymbol{\theta}}_\lambda = \bigl(X^\top X + \lambda I\bigr)^{-1} X^\top \boldsymbol{y}$$ where $X \in \mathbb{R}^{m \times (n+1)}$ is the design matrix. The matrix $(X^\top X + \lambda I)$ is always positive definite for $\lambda > 0$, so the inverse exists even when $X^\top X$ is rank-deficient. This is an additional benefit of regularization: it stabilizes the normal equations.

Proof

In matrix form, $J_\lambda(\boldsymbol{\theta}) = \frac{1}{2}\|\boldsymbol{y} - X\boldsymbol{\theta}\|^2 + \frac{\lambda}{2}\|\boldsymbol{\theta}\|^2$. Taking the gradient: $\nabla_{\boldsymbol{\theta}} J_\lambda = -X^\top(\boldsymbol{y} - X\boldsymbol{\theta}) + \lambda\boldsymbol{\theta} = (X^\top X + \lambda I)\boldsymbol{\theta} - X^\top\boldsymbol{y}$. Setting equal to zero gives the stated solution. For $\lambda > 0$, $X^\top X + \lambda I \succ 0$ since $X^\top X \succeq 0$ and $\lambda I \succ 0$, so the inverse exists. □

7.2.2 Regularization for Logistic Regression and GLMs

Regularization applies equally to classification. For logistic regression, the original objective was to maximize the conditional log-likelihood. With $\ell_2$ regularization, we maximize a penalized version:

Definition · Regularized Logistic Regression Objective

For binary logistic regression with $m$ training examples, the regularized objective is: $$\hat{\boldsymbol{\theta}} = \operatorname*{arg\,max}_{\boldsymbol{\theta}} \sum_{i=1}^{m}\bigl[y^{(i)}\log h_{\boldsymbol{\theta}}(\boldsymbol{x}^{(i)}) + (1-y^{(i)})\log(1 - h_{\boldsymbol{\theta}}(\boldsymbol{x}^{(i)}))\bigr] - \frac{\lambda}{2}\|\boldsymbol{\theta}\|_2^2$$ where $h_{\boldsymbol{\theta}}(\boldsymbol{x}) = \sigma(\boldsymbol{\theta}^\top\boldsymbol{x})$. The subtracted penalty $-\frac{\lambda}{2}\|\boldsymbol{\theta}\|^2$ shrinks parameters toward zero as $\lambda$ increases, equivalent to minimizing the negative log-likelihood plus $\frac{\lambda}{2}\|\boldsymbol{\theta}\|^2$.

Regularization is especially critical for text classification, where the number of features $n$ (vocabulary size, often $10{,}000$) can vastly exceed the number of training examples $m$ (often a few hundred). Without regularization, logistic regression badly overfits in this high-dimensional regime. With regularization, logistic regression on text typically outperforms Naïve Bayes (as studied in Section 5.3) in classification accuracy while remaining computationally efficient via gradient descent.

Warning · Feature Scaling Before Regularization

The $\ell_2$ penalty $\lambda\|\boldsymbol{\theta}\|^2 = \lambda\sum_j \theta_j^2$ applies the same pressure to every parameter. If features are on very different scales — say $x_1$ ranges from 1 to 10,000 (house size in sq. ft.) while $x_2$ ranges from 1 to 5 (number of bedrooms) — then $\theta_1$ will naturally be small to account for the scale and $\theta_2$ large, and the regularization will disproportionately shrink $\theta_2$. Always normalize features to zero mean and unit variance ($\hat{x}_j = (x_j - \mu_j)/\sigma_j$) before applying regularization. This also accelerates gradient descent.

7.2.3 Bayesian Interpretation: MAP Estimation

There is a beautiful probabilistic interpretation of regularization. Recall from Sections 1–5 that maximum likelihood estimation (MLE) finds the parameters that maximize $p(\mathcal{S} \mid \boldsymbol{\theta})$. What if we instead seek the parameters that are most probable given the data? By Bayes' rule: $$p(\boldsymbol{\theta} \mid \mathcal{S}) \propto p(\mathcal{S} \mid \boldsymbol{\theta})\, p(\boldsymbol{\theta}).$$ The value that maximizes this posterior is called the maximum a posteriori (MAP) estimator.

Theorem · $\ell_2$ Regularization = MAP with Gaussian Prior

Suppose $\boldsymbol{\theta} \sim \mathcal{N}(\boldsymbol{0},\, \tau^2 I)$ is the prior over parameters and $p(\mathcal{S} \mid \boldsymbol{\theta})$ is the likelihood (Gaussian for linear regression, Bernoulli logistic for classification). Then the MAP estimator: $$\hat{\boldsymbol{\theta}}_{\text{MAP}} = \operatorname*{arg\,max}_{\boldsymbol{\theta}} \log p(\mathcal{S} \mid \boldsymbol{\theta}) + \log p(\boldsymbol{\theta})$$ equals the $\ell_2$-regularized MLE with $\lambda = 1/\tau^2$. The Gaussian prior is the probabilistic expression of the belief that parameters should be small, and $\tau^2$ encodes how large we expect them to be a priori.

Proof

For a Gaussian prior $p(\boldsymbol{\theta}) \propto \exp(-\|\boldsymbol{\theta}\|^2/(2\tau^2))$, the log-prior is $\log p(\boldsymbol{\theta}) = -\|\boldsymbol{\theta}\|^2/(2\tau^2) + \text{const}$. Maximizing $\log p(\mathcal{S}\mid\boldsymbol{\theta}) - \|\boldsymbol{\theta}\|^2/(2\tau^2)$ is equivalent to minimizing $-\log p(\mathcal{S}\mid\boldsymbol{\theta}) + \frac{1}{2\tau^2}\|\boldsymbol{\theta}\|^2$. Setting $\lambda = 1/\tau^2$ recovers the $\ell_2$-regularized objective. □

💡
Frequentist vs. Bayesian: A frequentist adds regularization as an algorithmic design choice to reduce variance; a Bayesian adds it as a consequence of a Gaussian prior belief about parameters. Both arrive at the same formula — the philosophical difference is in why they do it. In practice, the MAP perspective is useful because it suggests alternative regularizers: a Laplace prior on $\boldsymbol{\theta}$ yields $\ell_1$ (Lasso) regularization, which promotes sparsity.

7.2.4 Why SVMs Resist Overfitting

A subtle but important observation connects regularization to the SVM studied in Chapter 6. The SVM primal objective was to minimize $\frac{1}{2}\|\boldsymbol{w}\|^2$ subject to margin constraints. This is precisely an $\ell_2$ penalty on the weight vector, ensuring that the parameters remain small even when the SVM operates in a kernel-expanded (potentially infinite-dimensional) feature space. It is this built-in regularization — not the kernel trick itself — that prevents SVMs from catastrophically overfitting in high dimensions. The formal argument invokes VC dimension: the class of all linear classifiers achieving a large geometric margin $\gamma$ has VC dimension bounded by $R^2/\gamma^2$ (where $R$ bounds the input radius), regardless of the ambient dimension. We return to this in the discussion section on learning theory.

Data Science Application · Regularization in Text Classification

Consider the task of email spam classification with $n = 10{,}000$ binary word-presence features and only $m = 100$ labeled training examples — a classic $n \gg m$ regime. Unregularized logistic regression will overfit perfectly (achieving 100% training accuracy) but generalize poorly. Logistic regression with $\ell_2$ regularization (choosing $\lambda$ by cross-validation on a dev set) typically achieves substantially better test accuracy than Naïve Bayes in this setting. The rule of thumb: without regularization, aim for $m \gtrsim 10n$; with regularization, you can often work with $m \ll n$.

7.3 Train, Dev, and Test Splits

The practical workflow of developing a learning algorithm requires making many decisions: which model class to use, what degree of polynomial to fit, what value of $\lambda$ to set, what features to include. Each decision is a form of model selection, and making these decisions correctly requires carefully partitioning your data to avoid circularity.

The central principle is simple: never evaluate on data that was used to make any algorithmic decision. If you use a dataset both to fit parameters and to estimate generalization performance, your performance estimate will be optimistically biased — you will report results that are better than what would be achieved on truly new data. This leads to a systematic three-way split.

7.3.1 Hold-Out Cross-Validation

Definition · Train / Dev / Test Split

Given a dataset $\mathcal{S}$, partition it into three disjoint subsets:

  • Training set $\mathcal{S}_\text{train}$: used to fit the model parameters $\hat{\boldsymbol{\theta}}$ for each candidate model.
  • Development set $\mathcal{S}_\text{dev}$ (also called validation or cross-validation set): used to select among candidate models (polynomial degree, $\lambda$, architecture, etc.).
  • Test set $\mathcal{S}_\text{test}$: used once, at the end, to report an unbiased estimate of the generalization error of the final selected model.
The procedure of training on $\mathcal{S}_\text{train}$ and selecting models based on $\mathcal{S}_\text{dev}$ is called hold-out cross-validation.

Figure 7.5. Illustration of the three-way data split. The full dataset (gray bar) is partitioned into a training set (blue, ~70%), a development/validation set (green, ~15%), and a test set (teal, ~15%). The training set fits model parameters; the dev set guides hyperparameter selection and architecture decisions; the test set provides a single, unbiased evaluation of the final model. Only the training set and dev set are consulted during development.

The algorithm is: train each candidate model $\mathcal{M}_k$ (e.g., degree-$k$ polynomial, or logistic regression with $\lambda_k$) on $\mathcal{S}_\text{train}$, producing hypothesis $h_k$. Compute error $\hat\varepsilon_\text{dev}(h_k)$ on $\mathcal{S}_\text{dev}$. Select $k^* = \operatorname*{arg\,min}_k \hat\varepsilon_\text{dev}(h_k)$. Report $\hat\varepsilon_\text{test}(h_{k^*})$ as the final performance estimate.

Example · Choosing Polynomial Degree via Dev Set

Setup. You have 500 housing price examples. You partition as: 350 training, 75 dev, 75 test. You consider polynomial degrees 1–5.

Results after training: dev errors (MSE) are 10.2, 5.1, 5.0, 4.9, 7.3 for degrees 1–5 respectively.

Selection. You select degree 4 (dev MSE 4.9). But is this really 4.9, or did you just get lucky from a small dev set? To get an honest estimate, you report the test error of the degree-4 model, which turns out to be 5.1.

Lesson. The dev error (4.9) is biased downward because the selection procedure picked the option that happened to look best on the dev set. The test error (5.1) is the honest number to report in an academic paper. The difference is small here, but on small dev sets or many competing models, the gap can be substantial.

7.3.2 Choosing Split Sizes

The question of how much data to allocate to each split is context-dependent. Historically, a rule of thumb of 70% / 15% / 15% or 60% / 20% / 20% was common. This remains reasonable for datasets of a few thousand examples.

Dataset sizeTypical train %Dev %Test %Guidance
100–1,00060–70%15–20%15–20%Consider k-fold CV instead
10,00070%15%15%Standard split
100,00080–90%5–10%5–10%Percentage shrinks; absolute size grows
1,000,000+95–99%0.5–2%0.5–2%10K examples usually sufficient for dev/test

The key insight for large datasets is that the absolute size of the dev and test sets matters more than the percentage. If algorithms differ in performance by 1%, you need roughly $1/0.01^2 = 10{,}000$ dev examples to reliably detect that difference at reasonable statistical power. If algorithms differ by 0.01% (as in online advertising click-through rate optimization), you may need millions. The prescription: choose dev and test sets large enough to measure the differences you care about detecting.

7.3.3 Rules for Using the Test Set

Warning · The Test Set Must Not Influence Any Decisions

The test set provides an unbiased generalization estimate only if no decision — model selection, feature engineering, hyperparameter tuning, architecture choice — was made based on test set performance. Every time you look at the test error and change your model in response, you "use up" some of the test set's validity as an unbiased estimator. This form of inadvertent overfitting affects even experienced researchers; the academic literature contains results that are likely slightly overfit to commonly-used benchmark test sets.

It is, however, legitimate to evaluate a fixed model on the test set multiple times — for instance, to track performance over time as a production system receives software updates. What matters is that test performance does not influence model decisions. Regularly reporting test metrics for monitoring purposes (e.g., weekly performance charts for a deployed system) is acceptable, as long as observed test performance does not cause you to revert to or prefer earlier models. When building a product (without needing to publish academic results), it is also perfectly reasonable to omit the test set entirely, acknowledging that the reported dev error is slightly optimistic.

Data Science Application · Benchmark Overfitting in Academic ML

The machine learning community routinely evaluates systems on shared benchmark datasets (CIFAR-10, ImageNet, SQuAD, etc.). Over years of competitive research, many teams optimize their systems based on incremental feedback from these benchmarks, effectively overfitting to the test set at a community level. A 2019 study found that a meaningful fraction of progress on CIFAR-10 over a decade was attributable to this inadvertent benchmark overfitting rather than genuine algorithmic improvements. This motivates the practice of releasing "held-out" test sets to which no team has access until after system designs are frozen.

7.4 k-Fold Cross-Validation

When the dataset is small, the simple hold-out split wastes data. Holding out 30% of an already small dataset of 100 examples means training on only 70 examples — and evaluating model selection on only 30 examples, which gives a noisy estimate. $k$-fold cross-validation addresses both problems by reusing data more efficiently: every example participates in both training and evaluation across multiple rounds.

7.4.1 The k-Fold Procedure

Definition · k-Fold Cross-Validation

Given a dataset $\mathcal{S} = \{(\boldsymbol{x}^{(i)}, y^{(i)})\}_{i=1}^m$ and a model class $\mathcal{M}$:

  1. Randomly partition $\mathcal{S}$ into $k$ equal-sized folds $\mathcal{F}_1, \ldots, \mathcal{F}_k$ (each of size $\lfloor m/k \rfloor$).
  2. For $j = 1, \ldots, k$: train $\mathcal{M}$ on $\mathcal{S} \setminus \mathcal{F}_j$ (i.e., all folds except $j$), evaluate on $\mathcal{F}_j$, obtaining error $\varepsilon_j$.
  3. Estimate the generalization error as $\hat{\varepsilon}_\text{CV} = \frac{1}{k}\sum_{j=1}^k \varepsilon_j$.
For model selection: repeat this procedure for each candidate model, select the model with lowest $\hat{\varepsilon}_\text{CV}$, then optionally refit on all $m$ examples. The typical choice is $k = 10$.

Figure 7.6. 5-fold cross-validation illustrated for a dataset partitioned into 5 equal blocks. In each of the 5 iterations (rows), one block (red, labeled "Test") is held out for evaluation; the remaining 4 blocks (blue, "Train") are used for fitting. The cross-validation estimate averages the 5 test errors. Every example participates in exactly $k-1 = 4$ training folds and exactly 1 test fold. For $k=10$, only 10% of the data is withheld in each iteration rather than 30% as in simple hold-out.
Example · 10-Fold CV for Polynomial Degree Selection

Setup. You have $m = 100$ examples and want to choose among polynomial degrees 1–5 using 10-fold CV.

Procedure. For each degree $d \in \{1, 2, 3, 4, 5\}$: partition data into 10 folds of 10 examples each. In fold $j=1$, train on examples 11–100, test on examples 1–10. In fold $j=2$, train on examples 1–10 and 21–100, test on 11–20. Repeat for all 10 folds, obtaining 10 test MSEs. Average them to get $\hat\varepsilon_d$.

Result. Suppose $\hat\varepsilon_1 = 9.8$, $\hat\varepsilon_2 = 5.1$, $\hat\varepsilon_3 = 5.2$, $\hat\varepsilon_4 = 5.7$, $\hat\varepsilon_5 = 7.3$. You select degree 2 and refit a quadratic on all 100 examples. Note: each fold uses 90 training examples — significantly more than the 70 you'd have with a simple 70/30 split.

7.4.2 Leave-One-Out Cross-Validation

Definition · Leave-One-Out Cross-Validation (LOOCV)

Leave-one-out cross-validation is the limiting case of $k$-fold CV with $k = m$. In each of the $m$ iterations, one example is held out as the test set and the model is trained on the remaining $m-1$ examples. The LOOCV estimate is: $$\hat{\varepsilon}_\text{LOO} = \frac{1}{m}\sum_{i=1}^{m} L(y^{(i)},\, \hat{f}_{-i}(\boldsymbol{x}^{(i)}))$$ where $\hat{f}_{-i}$ is the model trained on all examples except $i$, and $L$ is the loss. LOOCV is nearly unbiased for the true generalization error but requires fitting the model $m$ times — practical only when $m$ is small (say $m \leq 100$) or the model fits very quickly.

7.4.3 When to Use Each Procedure

ProcedureData requirementComputational costRecommended when
Simple hold-outLarge ($m \geq 10{,}000$)Train once per modelLarge datasets; fast turnaround needed
$k$-fold CV ($k=10$)Medium ($m \approx 100$–$10{,}000$)Train $k$ times per modelStandard small/medium datasets

Intuition · Why Are the k Estimates Correlated?

In $k$-fold CV, the $k$ estimates are not independent: any two adjacent folds share $k-2$ of their $k-1$ training folds. This means computing the variance of the $k$ estimates is more subtle than for independent estimates. Research by Kearns and others shows the estimates are positively correlated, so the empirical variance of the $k$ numbers underestimates the true variance of $\hat\varepsilon_\text{CV}$. For most practical purposes this is a minor concern, but it means that $k$-fold CV does not provide a statistically clean confidence interval for generalization error without additional correction.

7.5 Feature Selection

Regularization controls model complexity by shrinking parameters; an alternative approach is to directly select which features to include. This is especially useful when you suspect that out of a large feature set, only a small subset is truly predictive. Including irrelevant features adds parameters without adding signal, contributing pure variance without reducing bias.

Feature selection is a special case of model selection: instead of choosing the polynomial degree or $\lambda$, you are choosing the subset $\mathcal{F} \subseteq \{1, \ldots, n\}$ of features to include. An exhaustive search over all $2^n$ subsets is intractable for large $n$, so in practice greedy algorithms are used.

7.5.1 Forward Search

Definition · Forward Feature Selection Algorithm

Initialize $\mathcal{F} = \emptyset$. Repeat until adding features no longer improves dev performance:

  1. For each feature $j \notin \mathcal{F}$: fit the model using features $\mathcal{F} \cup \{j\}$ on $\mathcal{S}_\text{train}$; evaluate on $\mathcal{S}_\text{dev}$.
  2. Let $j^* = \operatorname*{arg\,min}_{j \notin \mathcal{F}} \hat\varepsilon_\text{dev}(\mathcal{F} \cup \{j\})$.
  3. If adding $j^*$ improves dev performance, set $\mathcal{F} \leftarrow \mathcal{F} \cup \{j^*\}$; otherwise stop.
Return the feature set $\mathcal{F}$ achieving the best dev performance across all iterations. Fitting the final model on $\mathcal{S}_\text{train} \cup \mathcal{S}_\text{dev}$ with selected features is optional.

Forward search is greedy: at each step it adds the single feature that most improves performance, committing to that choice before considering other features. This can miss cases where two features together provide complementary information but neither is useful alone. However, in practice the algorithm performs surprisingly well and is widely used as a first approach to feature selection.

Figure 7.7. Dev set accuracy (blue line, circle markers) during forward feature selection, as the number of selected features grows from 0 to 10. Accuracy rises steeply as the first few informative features are added, then plateaus and eventually decreases as additional features add noise. The red dashed line marks the optimal at 6 features selected. Adding more features beyond this point hurts generalization due to increased variance.
Example · Forward Search for Truck Failure Prediction

Setup. A logistics company measures 500 sensor variables on trucks to predict imminent engine failure. They suspect only ~10 sensors are truly predictive. They have $m = 200$ labeled examples.

Iteration 1. Try adding each of 500 features to the empty set, fitting 500 logistic regression models and evaluating each on the dev set. Suppose feature $x_{47}$ (oil pressure variance) gives the best dev accuracy of 72%. Set $\mathcal{F} = \{47\}$.

Iteration 2. Try adding each of the remaining 499 features. Feature $x_{213}$ (coolant temperature trend) gives the best dev accuracy of 81% when combined with $x_{47}$. Set $\mathcal{F} = \{47, 213\}$.

Stopping. After 11 iterations, adding any additional feature no longer improves dev accuracy. The algorithm returns a set of 11 features, and the final logistic regression model is refit on all available data using these 11 features.

Interpretation. Rather than fitting 500 parameters (likely to overfit with $m=200$), the model uses only 11 carefully selected features plus a bias term — a far more regularized model, arrived at through explicit feature selection rather than parameter shrinkage.

7.5.2 Backward Search and Computational Complexity

Definition · Backward Feature Elimination

Backward search starts with the full feature set $\mathcal{F} = \{1, \ldots, n\}$ and at each step removes the feature whose removal most improves dev performance (or least hurts it). The procedure terminates when no removal improves dev performance. Backward search can identify interactions between features that forward search might miss, but requires fitting $n, n-1, n-2, \ldots$ models per step, which is more expensive for large $n$.

The computational cost of forward search over $T$ selected features from $n$ total features is $O(T \cdot n)$ model fits. For text classification with $n = 10{,}000$ features and selecting $T = 50$, this requires $50 \times 10{,}000 = 500{,}000$ model evaluations — feasible with fast linear models but expensive with complex ones. In high-dimensional settings ($n \gg m$), regularization (Section 7.2) is often preferred over feature selection as it is more computationally efficient. However, feature selection provides interpretable results — the practitioner knows exactly which features are used — while regularization does not sparsify the parameter vector unless $\ell_1$ (Lasso) regularization is used.

Data Science Application · Feature Selection in Computational Biology

Genomics datasets often have $n \sim 20{,}000$ gene expression features but only $m \sim 100$ patient samples — a paradigmatic $n \gg m$ setting. Feature selection (identifying a small number of differentially expressed genes) is both a statistical necessity (reducing variance) and a scientific goal (understanding which genes drive the disease). Both forward search and $\ell_1$-regularized logistic regression (Lasso) are widely used, often producing overlapping but not identical selected gene sets. The dev set (via cross-validation) guides feature count selection, while the test set provides honest performance estimates for clinical translation.

✦ Chapter Summary

This chapter developed the conceptual and practical foundations for diagnosing and correcting poor generalization in learning algorithms. Bias and variance are the two fundamental failure modes: high-bias models underfit by making strong incorrect assumptions; high-variance models overfit by memorizing training noise. The bias–variance decomposition shows that expected test error decomposes exactly into these two terms plus irreducible noise. Regularization ($\ell_2$ penalty on parameters) is the most widely applicable remedy for high variance, and it has a principled Bayesian interpretation as MAP estimation with a Gaussian prior. Data splitting — train, dev, and test — provides the infrastructure for model selection without contaminating the final performance estimate. $k$-fold cross-validation makes this efficient for small datasets. Forward feature selection provides interpretable model selection when irrelevant features are suspected. These tools apply universally across all learning algorithms studied in this course: linear regression, logistic regression, GDA, Naïve Bayes, and SVMs.

BIAS

Systematic error from incorrect model assumptions. $\text{Bias}(\hat{f}(\boldsymbol{x})) = \mathbb{E}[\hat{f}(\boldsymbol{x})] - f^*(\boldsymbol{x})$. High bias means both training and dev errors are high. The fix: increase model complexity, add features, reduce regularization.

VARIANCE

Sensitivity of $\hat{f}$ to the particular training set. $\text{Var}(\hat{f}) = \mathbb{E}[(\hat{f} - \mathbb{E}[\hat{f}])^2]$. High variance means training error is low but dev error is much higher. The fix: reduce complexity, add regularization, collect more data, or select fewer features.

BIAS–VARIANCE DECOMPOSITION

For squared loss: $\mathbb{E}[(y - \hat{f})^2] = \text{Bias}^2 + \text{Var} + \sigma^2$. The three terms are independent. No algorithm can beat the irreducible noise $\sigma^2$. Optimal complexity minimizes $\text{Bias}^2 + \text{Var}$.

L2 REGULARIZATION

Penalizes large parameters: $J_\lambda(\boldsymbol{\theta}) = J(\boldsymbol{\theta}) + \frac{\lambda}{2}\|\boldsymbol{\theta}\|^2$. For linear regression, the closed-form solution is $\hat{\boldsymbol{\theta}} = (X^\top X + \lambda I)^{-1}X^\top\boldsymbol{y}$. Ridge regression is always invertible for $\lambda > 0$, even when $X^\top X$ is rank-deficient.

MAP ESTIMATION

Regularization equals MAP with a Gaussian prior: $\hat{\boldsymbol{\theta}}_\text{MAP} = \operatorname*{arg\,max}_\theta \log p(\mathcal{S}\mid\boldsymbol{\theta}) + \log p(\boldsymbol{\theta})$, where $p(\boldsymbol{\theta}) = \mathcal{N}(\boldsymbol{0}, \tau^2 I)$ gives $\lambda = 1/\tau^2$. A Laplace prior yields $\ell_1$ (Lasso) regularization and sparse solutions.

TRAIN / DEV / TEST SPLIT

Training set: fit parameters. Dev set: select model and hyperparameters. Test set: report unbiased generalization error. The test set must not influence any decision. Rule of thumb: 70/15/15% for small data; larger datasets warrant shrinking dev/test to a few thousand examples each.

k-FOLD CROSS-VALIDATION

Partition data into $k$ folds; train on $k-1$, test on the remaining 1, repeat $k$ times, average errors. Estimates $\hat\varepsilon_\text{CV} = \frac{1}{k}\sum_j \varepsilon_j$. Standard choice: $k=10$. More efficient than hold-out for small data, but computationally $k\times$ more expensive. Use LOOCV ($k=m$) when $m \leq 100$.

LEAVE-ONE-OUT CV

Extreme case $k = m$: train on $m-1$, test on 1, repeat $m$ times. Nearly unbiased estimator of generalization error. Computationally expensive ($m$ model fits per candidate). Practical only for very small datasets ($m \leq 100$) or very fast models.

FORWARD FEATURE SELECTION

Greedy search: start with $\mathcal{F} = \emptyset$, at each step add the feature that most improves dev performance. Cost: $O(T \cdot n)$ model fits where $T$ = selected features, $n$ = total features. Best when you suspect many features are irrelevant and interpretability matters.

DEV SET SIZE RULE

Choose dev and test sets large enough to reliably detect expected performance differences between algorithms. To distinguish a difference of size $\delta$ at reasonable power, you need $\sim 1/\delta^2$ examples. For large datasets, use absolute size rather than percentage as the criterion.
